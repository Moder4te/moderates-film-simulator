Moderate’s Film Simulator
코드 해부와 평가

디지털 사진에 아날로그 필름의 광학적·화학적 특성을 재현하는 Photoshop UXP 플러그인. 색을 눈대중으로 만들지 않고 제조사 기술자료(TDS)의 D-logE 특성곡선에서 유도한다. 이 문서는 저장소 전체를 읽고 무슨 역할을 하는지, 어떻게 쓰는지, 어디가 깨져 있는지를 정리한 것이다.

Kodak Portra 400의 실제 TDS 수치(core/color/films.js)를 그대로 그린 것이다. 세 곡선의 절대 위치가 아니라 기울기 차이가 곧 색이다 — 청감층이 가장 가파르므로 하이라이트로 갈수록 청색 농도가 빨리 올라가고, 인화 뒤 하이라이트가 따뜻해진다. 필름마다 다른 “색감”의 정체가 이것이고, 이 프로젝트가 TDS 수치를 그대로 쓰는 이유다.

무엇인가 층 구조 색 파이프라인 마감 파이프라인 모듈 지도 사용법 검사 스위트 발견한 결함 이미 알려진 한계 종합 점수

무엇인가

두 개의 플러그인, 하나의 순수 계산 코어

저장소는 Photoshop 플러그인 두 개, Lightroom Classic 플러그인 하나, 그리고 그 셋이 공유하는 순수 JavaScript 계산 코어로 이루어져 있다. 코어에는 photoshop·uxp·DOM 접근이 한 줄도 없고, 그 사실을 정적 검사가 강제한다. 그래서 색을 만드는 코드 전부를 Node에서 그대로 돌려 값으로 대조할 수 있다 — 이 프로젝트의 검증 가능성이 전부 여기서 나온다.

엔진 · com.filmsim.photoshop

색을 정한다

필름 유제 → 인화지 → 스캐너 → 사용자 색 조정을 3D LUT 한 장에 굽고 픽셀 레이어로 올린다. .cube·Lightroom 프로파일로도 같은 표를 뽑는다. 입력은 16bit ProPhoto.

마감 · com.filmsim.finish

매체를 얹는다

그레이딩 → 디퓨전 → 할레이션 → 그레인. 색 코드가 물리적으로 들어 있지 않다 (lib/에 core/color를 아예 복사하지 않는다). 8bit JPEG이 정상 입력이다.

lrplugin

프로파일을 나른다

색을 계산하지 않는다. 엔진이 구운 .xmp 36종(필름 9 × 스캐너 2 × 입력 가정 2)을 담아 설치·적용만 한다. LrC SDK가 픽셀에 접근할 수 없기 때문이다.

두 Photoshop 플러그인은 같은 문서에 겹쳐 쓰는 것이 정상이다. 레이어 접두사가 FilmSim Color / FilmSim Finish로 갈려 서로의 결과를 지우지 않는다. 나눈 이유는 명확하다 — 색은 순수 계산이고 마감은 Photoshop 액션이라, 섞여 있으면 마감을 손보다 색이 망가지고 그 실수는 결과를 보기 전까지 드러나지 않는다.

색 파이프라인 · core/color/film.js

격자점 하나가 지나는 일곱 단계

buildLut()이 필름 정의 하나를 size³ × 3 Float32 표로 굽는다. 1–4단계는 채널끼리 독립이라 축마다 한 번씩만 계산하고, size³ 루프에는 크로스토크와 인코딩만 남는다. 33³ 생성이 1ms라 캐시가 필요 없다.

  1. 인코딩 해제

    문서 코드값을 선형 광량으로 되돌린다. 어떤 전달함수를 쓸지는 core/color/inputs.js가 소유한다 — ProPhoto γ1.8(기본), 리니어 +4/+5/+6스톱, ACR 역산, S-Log3.

    L = decode(v)

  2. 로그 노광

    18% 그레이를 H = 0에 앵커한다. 이 지점이 곧 TDS의 Log H Ref = “박스 스피드 정상 노광”이다. 텅스텐 필름은 여기에 캐스트가 더해진다.

    H = log₁₀(L / 0.18) + 노광시프트 + tungstenCast

  3. 특성곡선

    TDS 샘플점을 PCHIP(단조 3차)으로 보간해 층별 농도를 얻는다. 일반 스플라인은 점 사이에서 튀어 없던 색 왜곡을 만들기 때문에 쓸 수 없다. PAVA 단조 보정이 도면상 물리적으로 불가능한 하강을 눌러 준다.

    D = curve(H)

  4. 인화 — 메인 톤을 잡는 자리

    이 단계가 모델의 핵심이다. 네거티브가 확대기 빛을 막고, 인화지가 그것을 받아 포지티브를 만든다. 밝은 피사체 → 네거 농도 높음 → 인화 노광 적음 → 인화지 발끝 → 밝은 인화물. 즉 인화지의 발끝이 하이라이트를, 어깨가 암부를 만든다. k는 채널별 인화 노광 = 확대기 색 필터이고, 이것이 오렌지 마스크를 상쇄한다.

    P = 10^(−paper(k − D))

  5. 크로스토크

    유제층 간 색 유출을 선형 공간에서 3×3으로 근사한다. 항등이면 곱셈을 건너뛴다.

    P′ = M · P

  6. 스캐너 스테이지 (튜닝값)

    레벨 → 틴트(암부·중간톤·명부 3점) → S커브 → 채도. Frontier와 Noritsu 두 종. 측정이 아니라 현상소 비교 문헌의 정성 서술을 옮긴 값이다 — 필름 룩의 상당 부분이 이 단계에서 나오므로 여기가 추정이면 결과물 전체가 추정이다. 기본값은 none.

  7. 화이트포인트 · 인코딩

    채널별 소프트 롤오프로 상한 근처만 눌러 1.0으로 수렴시킨다. 실측 곡선 인화지(Endura)를 고르면 이 단계를 끈다 — 인화지 발끝이 그 역할을 물리적으로 하므로 둘 다 걸면 이중 압축이다.

    v′ = P′^(1/1.8)

그 위에 얹히는 두 가지

사용자 색 조정(그레이딩). 색역별 CMY·채널 게인·발끝/어깨를 bakeGrading이 완성된 LUT 위에 굽는다. 판정은 sRGB 대리색으로 하고 적용은 클램프하지 않은 선형광에 한다 — 이전 구현은 왕복 전체를 sRGB에서 해서 33³ 격자점의 82.5%가 잘려 나갔다.

닷지·번(실험적). 필름의 H→D 응답은 건드리지 않고 인화 직전에 딱 한 지점만 끼운다 — 세 채널 농도 델타의 평균(luma)만 tanh로 압축하고 채널 간 편차(=색)는 그대로 더해 돌려준다. 채널마다 따로 압축하면 채도가 같이 눌린다. 기본은 꺼짐.

순서가 결과를 결정한다

네 단계의 순서는 취향이 아니라 제약이다. 하나라도 자리를 바꾸면 되돌릴 수 없는 스탬프가 잘못된 시점의 픽셀을 굽는다.

  1. 그레이딩 core/optics/tone.js

    노출·색온도만 선형광에서, 나머지는 인코딩 공간에서. 채널 체인 전체를 1D LUT으로 구워 안쪽 루프에 Math.pow를 하나도 남기지 않는다 (24MP 4.4초 → 0.88초). 양자화는 마지막 한 번, 8bit에는 TPDF 디더 (평균 띠폭 35.3px → 2.3px). 제일 앞이어야 할레이션이 조정된 하이라이트에서 발생한다.

  2. 디퓨전 core/optics/displace.js

    해상도를 입자 크기에 묶어 razor 엣지를 없앤다. 기본은 변위 방식 — 입자 크기 셀 단위로 이웃을 무작위로 집어 미세 선을 조각낸다(블러는 흐리게 남긴다). 할레이션보다 먼저여야 한다 — 합성본을 스탬프하므로 할레이션이 이미 있으면 그 픽셀이 구워져 나중에 끌 수 없다.

  3. 할레이션 apps/finish/src/halation.js

    Core(×0.3 Color Dodge) · Mid(×1.1 Linear Dodge) · Bleed(×4.0 Linear Dodge) 세 스케일. 추출은 적색 채널 구동이다 — 휘도로 뽑으면 포화 적색 네온이 임계에 안 걸린다. 소스를 애초에 오렌지-레드로 칠해 채널 확산차가 만든 붉은 링을 살린다. 원반(Maximum 필터)으로 경계를 세우고, 넓은 스케일은 1/2·1/4 해상도에서 계산한다.

  4. 그레인 core/optics/grainfield.js

    값 노이즈로 생성한다 — 블러는 반경을 키우면 대비가 함께 떨어져 mush가 되지만 값 노이즈는 셀을 키우면 대비를 유지한 채 blob이 실제로 커진다. 텍스처 한 벌을 세 존(암부·중간톤·명부)이 Overlay + Blend If로 나눠 쓰고, 교차점 2개에서 존 범위를 유도해 가중치 합이 항상 정확히 1이다.

입자 크기는 물리로 나온다

µm        = 10 · (ISO/400)^0.44        감도 → 필름면 유효 입자 지름 (4~25µm)
px_per_mm = 이미지_긴변_px / 프레임_긴변_mm
grain_px  = (µm / 1000) × px_per_mm

입자 크기는 필름면에서 고정이다. 최종 이미지에서 달라 보이는 것은 확대율 차이다 — 4×5는 35mm보다 프레임이 3.5배 크니 같은 출력 크기까지 확대할 때 배율이 1/3.5이고 입자도 그만큼 곱게 보인다. 할레이션 반경도 같은 배율을 쓴다.

사용법

색 먼저, 마감 나중

마감의 디퓨전 레이어는 그 시점 화면을 구운 파괴적 스탬프라, 그 뒤에 색을 적용하면 이미 구워진 픽셀을 다시 칠할 수 없다. 순서를 어기면 색이 중복되거나 안 먹은 것처럼 보인다.

  1. 설치

    Photoshop 2023(v24) 이상. 릴리스의 .ccx를 더블클릭한다. 재시작하면 Film Sim 엔진 · 미리보기 · 분포 · 마감 네 패널이 뜬다. 필요한 것만 설치해도 동작한다.

  2. 「중립 현상」으로 raw를 푼다

    엔진은 입력의 전달함수가 감마 1.8 거듭제곱 하나뿐이라고 전제한다. Camera Raw는 슬라이더를 전부 0으로 둬도 이 조건을 만족하지 않는다(실측: 암부 +0.62 / 명부 −0.24스톱의 S자 대비 커브). 세 가지 길이 있다.

    # 공식 경로 — ACR을 아예 안 거친다
pip install rawpy numpy tifffile
python tools/decode-raw.py in.ARW out.tiff        # 기본 헤드룸 +5스톱
python tools/decode-raw-gui.py                    # 좌표를 클릭으로 잡는 GUI

    출력 TIFF는 Photoshop에서 프로파일 지정 → ProPhoto RGB로 지정하고, 패널의 입력 소스를 도구와 같은 헤드룸(「리니어 +5스톱」)으로 맞춘다. 어긋나면 노광이 통째로 밀린다. 외부 도구 없이 가려면 ACR로 “Adobe Standard” + 슬라이더 0으로 현상한 뒤 입력 소스를 「ACR Adobe Standard (역산)」로 고른다 — 단 알려진 계조 버그가 있다.

  3. 엔진 — 색을 정한다

    필름 · 입력 소스 · 인화지 · 스캐너를 칩으로 고르고 노광을 맞춘 뒤 [현재 문서에 적용]. 컬러휠에서 대표색 마커를 끌면 그 색역의 CMY가 조절된다. 피부톤은 색상각+채도 창으로 잡는 별도 색역이고, 전경색 스포이드로 중심 각을 옮길 수 있다. 미리보기 패널은 색만 반영한다(할레이션·그레인은 공간 연산이라 제외). 분포 패널은 적용 결과의 색이 색상·채도 평면에 어떻게 퍼져 있는지 보여준다.

  4. 마감 — 매체를 얹는다

    매체(필름 포맷 · 입자 크기 기준) → 할레이션 → 그레인 순으로 조절하고 적용한다. 작업 파일과 최종 출력 크기가 다르면 출력 크기로 리사이즈한 뒤 마감을 적용하거나, “입자 크기 기준”에 최종 긴 변을 직접 지정한다. 배치는 출력 폴더가 원본 폴더와 같으면 실행 전에 거부하고, 저장 직전에 파일 단위로 한 번 더 본다.

  5. 내보내기

    .cube — 33³/65³. “적용”과 같은 결과다. Sony S-Log3을 고르면 로그 촬영본에 바로 거는 룩 LUT이 된다(비대칭 LUT이라 “적용”과 다른 소스다). Photoshop에서는 조정 레이어 → 색상 검색 → 3DLUT 로드 — GPU 가속 + 비파괴라 대용량에서 픽셀 적용보다 빠르다.

    Lightroom 프로파일(.xmp) — 입력 가정을 고르고 세트 전체를 굽는다. ACR 역산(정확)과 하이브리드(ACR 커브 그대로 — 고대비 장면에서 오히려 보기 좋을 때가 있다) 두 가지다. 프로파일은 격자 32³ 고정 — ACR이 어떤 크기를 넣어도 32로 리샘플하므로 처음부터 32로 구워 보간을 한 번 줄인다.

  6. 개발

    node tools/sync-libs.js    # core/를 고쳤으면 반드시 — 각 앱 lib/로 복사
node tools/check.js        # 문법·경계·경로·로드·함수·정합성·톤·그레인. 3초
node tools/build-lrplugin.js   # dist/FilmSim.lrplugin/ — 프로파일 36종을 굽는다

uxp service start          # 별도 터미널. 떠 있어야 packaging이 된다
node tools/build-ccx.js
uxp service stop           # 반드시 끈다 — 켜져 있으면 UDT가 플러그인을 못 올린다

노광 슬라이더가 정확히 0을 만들 수 없고, 그 값이 파일명에 새어 나간다

중간

apps/engine/index.html:411 (data-step="0.333") · shared/ui/cslider.js:55-57

x = Math.round((x - min) / step) * step + min;   // min=-2, max=2, step=0.333
quantize(0)  →  -0.002
도달 가능한 값: … -0.668, -0.335, -0.002, 0.331, 0.664 …   (0 이 없다)
증상
슬라이더를 한 번 만지면 film.exposure가 다시는 정확히 0이 되지 않는다. 더블탭 리셋도 defaultValue = quantize(0) = -0.002라 소용없다.
영향
색 자체는 0.002스톱이라 무시할 수준이다. 문제는 이름이다 — cube.suggestName·cube.title·xmp.profileName이 전부 if (ev)로 판정하므로, 내보낸 파일과 Lightroom Profile Browser 항목에 -0.002EV가 붙는다.
고치기
최소 수정은 data-step을 4의 약수로 바꾸는 것(0.25 또는 0.5). 1/3스톱 눈금을 유지하려면 cslider.quantize가 min이 아니라 0을 기준으로 스냅하게 하거나, 이름 판정을 Math.abs(ev) >= 0.005로 바꾼다.

가장 값진 것 하나만 꼽으면

“통과했다는 것이 검사가 실제로 돈다는 뜻은 아니다”를 코드에 새겨 둔 태도다. 코너 8점 일치를 보고 XMP 포맷이 맞다고 판단했다가 그 8점이 잘못된 가설도 통과시킨다는 것을 나중에 발견한 기록이 core/io/xmp.js에 그대로 남아 있다. 그 경험이 “검사를 일부러 깨뜨려 확인한다”는 규칙으로 굳었고, 그 규칙이 다시 check-conformance의 구조 검사(값이 아니라 “몇 군데서 부르는가”)로 이어졌다. 이건 흉내로 나오는 게 아니다.

다음에 손댈 순서를 굳이 정한다면

  • 지금 당장 — 캐시 키에 dodgeBurn 추가, .cube 이중 확장자, 노광 슬라이더 step. 세 줄이면 끝나고 셋 다 사용자 눈에 보인다.
  • 그다음 — 분석 경로의 레이어 격리와 dispose를 host/ps.js의 헬퍼 하나로 합친다. 이 저장소가 반복해서 낸 결함이 “구현이 둘이 되면 갈라진다”이고, 여기가 지금 갈라져 있는 자리다.
  • 구조적으로 — check-boundaries에 “캐시 키 검사”를 하나 더 붙일 수 있다. 결과에 영향을 주는 params.film 필드 목록과 visualTables의 키 배열을 대조하면, 이번 1번 같은 결함은 다시는 사람 눈에 의존하지 않아도 된다.
  • 가장 큰 것 — N4(ACR 역산 계조 깨짐)와 A1(스캐너 측정). 둘 다 코드가 아니라 데이터를 다시 찍는 일이라 시간이 든다. 그러나 위 점수에서 깎인 20점 중 절반이 여기 있다.
