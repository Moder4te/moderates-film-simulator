## 1. 배치 적용이 원본을 덮어쓸 수 있다 — 심각

`apps/finish/src/batch.js:79`

```js
if (outputFolder.nativePath === sourceFolder.nativePath) {
  throw new Error("출력 폴더가 원본 폴더와 같습니다. 다른 폴더를 선택하세요.");
}
```

동일 폴더 방어가 **경로 문자열 완전 일치** 하나뿐이다. 다음 중 하나만 어긋나도 통과한다.

- Windows 대소문자 (`C:\Photos` vs `C:\photos`)
- 후행 경로 구분자
- 심볼릭 링크 · 네트워크 드라이브 별칭 · 매핑된 드라이브

통과하면 곧바로 원본이 지워진다.

- `outputName()` (`:35`) — `prefix`는 UI에서 **아예 전달되지 않고**(`apps/finish/src/main.js:274`),
  `suffix` 기본값 `""`, `format` 기본값 `"jpg"`. 즉 **기본 설정에서 출력 파일명이
  원본과 완전히 동일**하다.
- `saveDocument()` (`:55`) — `createFile(name, { overwrite: true })`.

`README.md`와 `docs/STATUS.md`는 "**원본은 어떤 경우에도 수정되지 않는다**"고 약속한다.
폴더 단위 검사로는 그 약속을 지킬 수 없다 — 방어는 **파일 단위**여야 한다.

**고치는 법.** `overwrite: false`로 두면 충돌한 장만 예외가 되어 `failed` 목록에 남고
나머지는 계속 진행된다. 이미 있는 "한 장이 실패해도 중단하지 않는다" 방침과 그대로 맞물린다.

```js
const target = await outFolder.createFile(name, { overwrite: false });
```

폴더 비교는 남겨 두되 **1차 방어**로만 다룬다. 진짜 방어선은 파일 이름 충돌이다.

## 2. 마감 앱의 `clearOwnLayers`가 재귀가 아니다 — 중간

`apps/finish/src/pipeline.js:36`

```js
const targets = doc.layers.filter((l) => l.name.startsWith(PREFIX));
```

엔진 쪽(`apps/engine/src/pipeline.js:44`)은 같은 일을 `collectLayers`로 **재귀** 처리하고,
그 이유를 주석에 못 박아 뒀다("사용자가 묶었거나 이전 버전이 그룹화한 경우").
`tools/check-boundaries.js:178`이 `l.layers` 존재를 정적으로 강제하기까지 한다.

마감 앱은 **자기가 `groupOwnLayers`로 그룹을 만들면서도**(`:45`) 노출이 동일한데
재귀도 없고 검사도 안 걸린다. 사용자가 `FilmSim Finish` 그룹을 다른 그룹 안으로
옮기면 재적용마다 그레인·할레이션이 누적된다 — 불변식 6이 막으려던 바로 그 결함이다.

엔진에만 있고 여기 없는 것 둘.

- `l.name` null 가드 (엔진: `l.name && l.name.startsWith(...)`)
- `layer.delete()`의 try/catch — 그룹 해제로 무효가 된 참조 하나가 재적용 전체를
  예외로 중단시킨다

## 3. 할레이션이 실패하면 검은 레이어가 남는다 — ~~중간~~ → 낮음

`apps/finish/src/halation.js:186`~`:271`

`base`(`FilmSim Finish · Halation src`)는 Normal 블렌드의 **불투명 전면 레이어**다.
주석도 "두면 원본 이미지를 덮는다"고 적어 놨고 마지막 줄에서 지운다.

```js
const base = await buildRedSource(...);
for (const sc of scales) { ... await play(cmds); }   // ← 여기서 던지면
await base.delete();                                  // ← 도달하지 못한다
```

루프 안의 `play()`(축소·채널 필터·블렌드) 중 하나라도 던지면 **사용자 문서 위에
전면 검정 레이어가 남는다.**

같은 파일의 `buildRedSource`(`:110`)는 이미 `finally`로 dispose를 지키고 있으니
패턴은 이미 있다. 스케일 루프 전체를 감싸면 된다.

```js
try {
  for (const sc of scales) { ... }
} finally {
  await base.delete();
}
```

### 심각도 재평가 — 처음에 과대평가했다

재실행하면 `clearOwnLayers`가 접두사로 지우기도 한다.

### #1 배치 원본 덮어쓰기

**방침 — 2단 방어.** 폴더 검사는 그대로 두고(1차) **파일 단위 검사를 추가한다**(2차).
폴더 비교는 별칭·대소문자에 뚫리므로 그것만으로는 보증이 성립하지 않는다.

> ⚠️ **`overwrite: false`로 바꾸는 것만으로는 안 된다.** 같은 출력 폴더에 설정을 바꿔
> **다시 돌리는 것은 정상 사용**인데, 그 경우 전부 "이미 존재함"으로 실패한다.
> 막아야 하는 것은 덮어쓰기 일반이 아니라 **원본 그 파일을 덮어쓰는 것** 하나다.

`apps/finish/src/batch.js`

```js
/**
 * 출력 파일이 원본 그 파일인가.
 *
 * 폴더 경로 비교(runBatch)는 대소문자·후행 구분자·심볼릭 링크에 뚫린다. 뚫리면
 * 기본 설정(prefix 없음·suffix ""·jpg)에서 출력 파일명이 원본과 **완전히 같아**
 * 원본이 지워진다. 그래서 실제 방어선은 여기다.
 *
 * 두 nativePath 모두 UXP 저장소 API가 준 실제 항목에서 나오므로 같은 규칙으로
 * 정규화돼 있다 — 사용자가 각각 고른 폴더 두 개를 비교하는 것과 다르다.
 */
async function isSameFile(outFolder, name, sourceEntry) {
  let existing;
  try {
    existing = await outFolder.getEntry(name);
  } catch (e) {
    return false; // 대상이 없으면 충돌 자체가 없다
  }
  return existing.nativePath === sourceEntry.nativePath;
}
```

`saveDocument`에 원본 엔트리를 넘기고 맨 앞에서 막는다.

```js
async function saveDocument(doc, outFolder, name, options, sourceEntry) {
  if (await isSameFile(outFolder, name, sourceEntry)) {
    throw new Error(`출력 파일이 원본과 같습니다: ${name} (접두사·접미사를 주거나 다른 폴더를 고르세요)`);
  }
  const target = await outFolder.createFile(name, { overwrite: true });
  ...
}
```

> **실제 구현은 이 코드보다 한 겹 두껍다.** 위 `isSameFile`은 `nativePath`를 `===`로
> 비교하는데, 그러면 **이 지시서가 지적한 바로 그 결함이 파일 단위에서 반복된다** —
> 두 폴더는 사용자가 각각 고른 것이라 대소문자가 다르면 `getEntry`가 돌려주는 경로도
> 다르다. 그래서 ① 비교를 `shared/paths.js`의 `samePath`(구분자·후행 구분자·Windows
> 대소문자 정규화)로 바꾸고 ② 경로가 달라도 **크기와 수정 시각이 정확히 일치**하면
> 같은 파일로 본다(심볼릭 링크·매핑 드라이브는 경로 문자열이 아예 다르다).

`runBatch`의 호출부(`:97`)에 `entry`를 추가한다. 던진 예외는 기존 `catch`가 받아
`failed` 목록에 남기고 **나머지 장은 계속 진행된다** — "한 장이 실패해도 중단하지
않는다"는 기존 방침에 그대로 얹힌다.

**같이 볼 것.** `collectFiles`는 루프 **전에** 목록을 확정하므로, 출력 폴더가 원본
폴더 안에 있어도 같은 실행에서 산출물을 다시 처리하지는 않는다. 그러나 **다음 실행에는
잡힌다.** 재귀 모드에서 출력 폴더를 원본 하위에 두지 말라는 경고를 UI에 한 줄 두는 것을
검토할 것(코드 변경은 아니다).

**실기 검증**

| # | 절차 | 기대 |
|---|---|---|
| 1 | 원본·출력을 **같은 폴더**로 지정 | 기존 폴더 검사가 실행 전에 거부 (회귀 없음) |
| 2 | Win: `C:\test` vs `C:\TEST` / mac: `ln -s ~/photos ~/photos-alias` 로 지정 | **폴더 검사는 통과**하고 **파일 검사가 전부 잡는다.** 원본 타임스탬프·크기 불변 확인 |

### #2 마감 `clearOwnLayers` 재귀

**왜 파괴적 단계라서 오히려 더 급한가.** 파괴성은 면죄부가 아니라 가중 사유다.

엔진은 산출물이 픽셀 레이어 한 장이라 중복 적용돼도 지우고 다시 하면 된다. 마감은
다르다 — 그룹을 못 찾아 그레인·할레이션이 겹쳐 쌓이면, **그 아래 디퓨전은 이미 그
시점 합성본을 구워 놓은 상태**라 되돌릴 지점이 없다. 방어가 더 필요한 쪽에 방어가
없고, `check-boundaries` 규칙 6도 덜 파괴적인 엔진에만 걸려 있다.

게다가 마감은 **자기가 `groupOwnLayers`로 그룹을 만든다**(`:45`). 중첩 가능성을 스스로
만들어 놓고 중첩을 못 찾는다.

**방침 — `collectLayers`를 `host/ps.js`로 올려 한 벌만 남긴다.**

지금 같은 함수가 **네 곳에 복사**돼 있다(`engine/pipeline.js:23` · `engine/apply.js:24` ·
`engine/preview.js:84`, 그리고 마감에는 아예 없다). 인자로 받은 트리를 훑을 뿐 `photoshop`을
require하지 않는 순수 함수이고, 두 앱 모두 이미 `../lib/host/ps`를 require하므로
`sync-libs.js`의 `LIBS`도 건드릴 필요가 없다.

```js
// host/ps.js
/** layers 트리를 재귀로 훑어 pred를 만족하는 레이어를 모은다(그룹 안까지). */
function collectLayers(layers, pred, out) {
  for (const l of layers || []) {
    if (pred(l)) out.push(l);
    const kids = l.layers;
    if (kids && kids.length) collectLayers(kids, pred, out);
  }
  return out;
}
```

`apps/finish/src/pipeline.js`

```js
async function clearOwnLayers(doc) {
  for (let guard = 0; guard < 12; guard++) {
    const targets = ps.collectLayers(doc.layers, (l) => l.name && l.name.startsWith(PREFIX), []);
    if (targets.length === 0) break;
    for (const layer of targets) {
      try {
        await layer.delete();
      } catch (e) {
        /* 그룹 해제로 이미 사라진 참조 — 다음 반복에서 다시 훑는다 */
      }
    }
  }
}
```

null 가드(`l.name &&`)와 try/catch도 함께 들어간다. 엔진에만 있던 것들이다.

> ⚠️ **`groupOwnLayers`는 재귀로 만들지 말 것.** 그 함수는 **방금 만든 최상위 레이어들**을
> 묶는 것이 목적이다. 재귀로 바꾸면 사용자가 다른 그룹 안에 넣어 둔 과거 마감 레이어까지
> 끌어내 묶어 버린다. `doc.layers.filter(...)` 그대로 두는 것이 맞다.

> ⚠️ **이 리팩터링은 현재 규칙 6 검사를 깨뜨린다.** `tools/check-boundaries.js:178`이
> `apps/engine/src/pipeline.js` 본문에서 `/l\.layers/`를 찾는데, `collectLayers`를 옮기면
> 그 파일에 그 문자열이 사라진다. 검사를 함께 고쳐야 한다 —
> `ps.collectLayers(` 호출을 찾는 쪽으로 바꾸고, **같은 검사를 마감 파이프라인에도 건다.**
> 이걸 빠뜨리면 `check.js`가 실패하거나(다행) 조용히 무의미해진다(위험).

## 인프라

`.github/` 워크플로가 없어 `node tools/check.js`가 순전히 수동이다.
검사 스위트가 이 정도로 잘 만들어져 있는데 push마다 안 도는 것은 아깝다 —
외부 의존성이 0이라(`package.json`조차 없다) 워크플로 파일 한 장이면 끝난다.

```yaml
# .github/workflows/check.yml
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: node tools/sync-libs.js
      - run: node tools/check.js
```

## 검사에서 확인된 것 (결함 아님)

되짚을 때 다시 의심하지 않도록 적어 둔다.

- **사면체 보간 6분기 전부 정확하다** (`core/color/lut.js:115-174`). 여섯 경로의
  누적 경로가 표준 알고리즘과 일치한다.
- **PCHIP + PAVA 단조 보정이 정확하다** (`core/color/curve.js`). Fritsch–Carlson
  조건, 가중 조화평균, 끝점 선형 외삽 모두 맞다.
- **md5 · adler32 · zlib stored · Adobe Base85 모두 정확하다** (`core/io/xmpcodec.js`).
  패딩 길이 계산이 경계값(len=55/56/0)에서 성립하고, 2^29 이상 길이의 상위 워드도
  처리한다. Base85의 리틀엔디언 + 최하위 우선 방향도 주석대로다.
- **필름 데이터가 설계와 일치한다.** 9종 전부 녹감층 실효대비가 1.000±0.001이다
  (`printGamma = 1/γ_G` 규약이 지켜지고 있다는 뜻).
- **`lrplugin/Install.lua`의 경로 조립이 양 플랫폼에서 맞다.** `WIN_ENV` 전역,
  `home` 기준 조립, 폴백 폴더 선택까지.
- **디더 · 색역 · 단조성 불변식이 실제로 검증되고 있다.** `check-tone.js`가
  역전 ≤1레벨 / 빈도 0.040% / 띠폭 35.3px→2.3px를 매번 재측정한다.
